# HTTP contract and host ports

The portable router uses Web `Request` and `Response`. `createAgendaRouter` receives an `AgendaService`, an explicit deployment mode, exact allowed origins, a durable rate limiter, an administrator subject allowlist and an optional trusted identity resolver. The service exposes its actual immutable configuration mode through the readonly `configurationMode` contract. The router requires that mode to match its deployment mode before any domain operation; a missing mode also fails closed. Production cannot serve fixture data and a local fixture administrator cannot access a production domain. No request header is interpreted as an administrator identity. Every production API endpoint fails closed without the server-side resolver and allowlist, including catalog and availability. Unconfigured mode makes no domain calls.

The API prefix is `/api/agenda/v1`. All responses use `Cache-Control: no-store`; errors have the shape `{ "error": { "code": "...", "message": "..." } }` and never include a SQL exception, capability or customer detail. No CORS origin is reflected or allowed with a wildcard. Body validation rejects unknown fields, limits actual UTF-8 bytes to 8192 by default, accepts JSON objects only, and bounds dates, identifiers and numbers. Query keys cannot repeat and only the fields documented below are accepted.

| Method | Path after prefix                | Contract                                                                                                                               |
| ------ | -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/catalog`                       | `Catalog`, including `configVersion` and explicit fixture/production mode                                                              |
| GET    | `/availability`                  | Query: `serviceId`, `date`, optional `professionalId`; returns `Availability`                                                          |
| POST   | `/bookings`                      | `CreateBookingInput` fields, client-generated `managementToken`, and `configVersion`; returns `BookingReceipt`                         |
| GET    | `/bookings/:id`                  | Customer capability required; returns `BookingReceipt`                                                                                 |
| POST   | `/bookings/:id/cancel`           | Customer capability, `expectedVersion`, `configVersion`                                                                                |
| POST   | `/bookings/:id/reschedule`       | Customer capability, `date`, `startMinute`, `professionalId`, `expectedVersion`, `configVersion`                                       |
| GET    | `/admin/schedule`                | Verified administrator; query `date`, optional `professionalId`, optional `includeCancelled=true\|false`; returns `{bookings, blocks}` |
| POST   | `/admin/walk-ins`                | Verified administrator; booking fields and `configVersion`; returns `BookingReceipt`                                                   |
| POST   | `/admin/blocks`                  | Verified administrator; `professionalId`, `date`, `startMinute`, `endMinute`, `label`, `configVersion`; returns `ScheduleBlock`        |
| POST   | `/admin/bookings/:id/cancel`     | Verified administrator; `expectedVersion`, `configVersion`                                                                             |
| POST   | `/admin/bookings/:id/reschedule` | Verified administrator; reschedule fields, `expectedVersion`, `configVersion`                                                          |
| POST   | `/admin/blocks/:id/cancel`       | Verified administrator; `expectedVersion`, `configVersion`                                                                             |
| GET    | `/admin/export`                  | Verified administrator; versioned `AgendaBackup` JSON attachment containing private data                                               |

Every POST requires an exact allowed `Origin`, `Content-Type: application/json`, and `Idempotency-Key` with 8–128 characters from letters, digits, `_`, `.`, `:`, and `-`. The first character is a letter or digit. The body includes the positive integer `configVersion` last reviewed by the caller. A retry preserves the complete body, original capability and key. `expectedVersion` protects each existing reservation or block against a lost update. A stale catalog, stale reservation, occupied interval or changed idempotency payload is a typed conflict rather than a successful reservation.

The official client creates a random 32-byte capability with WebCrypto, encodes it as canonical unpadded base64url, and sends it as `managementToken` in the creation body. The router passes only its SHA-256 hexadecimal digest to the domain. The raw capability is never returned, stored in a backup, logged or accepted in a query parameter. Customer reads and changes use `Authorization: Bearer <capability>`; authorization checks the requested reservation ID and digest before retrieving or changing it. This bearer token grants no administrator access. A management link may keep the capability in the URL fragment, which is not sent to the server; the client keeps it in memory and must not persist it in shared browser storage.

`TrustedIdentityResolver.resolve(request, context)` is a host integration port. The host must verify the principal before returning its stable subject. The router requires that exact subject in the server-configured allowlist. Client-provided identity headers, names or capabilities cannot satisfy this contract. Sites documents dispatcher-owned identity, but consuming it safely and packaging the existing assets is still host integration work; see the [handoff](../../docs/agenda/hosting-handoff.md). Neither current adapter invents a credential, OAuth provider or identity header.

`createSqlRateLimiter` uses atomic SQL upserts and global time buckets: 30 public booking requests, 60 customer management requests and 120 administrator mutations/exports per minute by default. Limits and windows are bounded configuration. Counters stop at their limit; expired rows are pruned in bounded batches. No IP address, subject, token or customer data appears in a rate bucket. This conservative global policy can throttle concurrent legitimate users and can be exhausted by an attacker; hosting-specific abuse controls need review before production activation. A rate-store failure prevents the mutation rather than bypassing the limit.

`startAgendaNodeServer` binds only `127.0.0.1` or `::1`. Fixture mode and its server-injected fixture administrator require explicit opt-in and are unavailable in a production process. The fixture identity checks the actual loopback socket, never a forwarded address. An exact configured Host check limits DNS rebinding; origin configuration derives from the bound loopback port or explicit trusted server configuration. `fallback` can supply the existing static assets at the same origin. Node production options require explicit `publicOrigin` and `allowedOrigins` and do not interpret proxy headers.

`createAgendaWorker` takes environment-to-service, rate-limiter, origin, allowlist and identity factories. It does not assume a D1 binding name, Cron, Queue, Durable Object, rate-limit binding or email runner. Hosted Worker fixture/unconfigured modes and production without the trusted identity resolver and allowlist return unavailable before initializing a service. Notifications remain a durable outbox concern with sending disabled; this transport starts no background sender. No backend has been deployed by this module.

`node --test agenda/tests/http.test.ts` exercises the real Node bridge and SQLite-backed full flow as well as bounded validation, capability isolation, trusted identity, global throttling, conflict rollback and retry behavior. These local checks do not establish that a host identity integration or live notification provider works.

## Staff role and absence increment

See [owner/barber authority and temporary absences](../../docs/agenda/staff-absence-roles.md) for the server-owned stable-subject map, session contract, own-agenda restrictions, absence endpoints, and immutable conflict snapshots. `/admin/schedule` now returns `{bookings, blocks, absences}`. Export is owner-only and produces backup version 2. The generic trusted identity port remains unchanged; client role headers cannot assign privileges. Fixture-only `AGENDA_FIXTURE_ROLE=barber` is available for local phone-layout tests.

## Private reschedule availability

`GET /bookings/:id/availability?date=YYYY-MM-DD&professionalId=ID` uses the existing `Authorization: Bearer` booking capability and customer-management rate limit. `professionalId` is optional. The domain enforces reservation scope, confirmed status and the customer change deadline, then uses the original booked duration/buffers and excludes only that reservation. Current professional eligibility, shifts, lead/horizon, other allocations and absences still apply. Responses are no-store and contain no private booking data or management token. Public `/availability` never accepts an arbitrary ignore-ID parameter. Availability remains advisory; the actual reschedule requires the reviewed configuration and expected version and commits atomically.
